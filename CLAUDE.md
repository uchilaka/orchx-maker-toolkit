# OrchX Maker Toolkit — Claude Code Context

This repo is a **Gemini CLI** skill distribution toolkit. See `GEMINI.md` for the project's mission, sprint history, and progress tracker — that file is Gemini's own working context doc and stays Gemini-scoped.

## Directory scope

- `.gemini/skills/` — Gemini CLI skill sources, the source of truth. Packaged into `dist/*.skill` via `mise run build:gemini` and installed with `gemini skills install`. The `SKILL.md` frontmatter format happens to be Claude-Code-compatible, but these are Gemini skills — don't treat them as Claude Code skills. Sits alongside `.claude/skills/` below by design, one dot-directory per harness.
- `dist/` — built Gemini `.skill` zip artifacts. Generated by `mise run build:gemini`, not hand-edited.
- `.claude/skills/` — Claude-native skills (currently: `patch-my-hosts`, `llm-wikify`, `browser-test-assist`, `browse`). Unrelated to `.gemini/skills/`. Not built, but published through the plugin below, except `browse`, which assumes the maintainer's `~/project-plans` and `~/pr-reviews` layout and is installed with `install:claude-global` only. Each one is either repo-specific or globally mounted — see "Creating a skill" below.
- `.claude-plugin/` — the Claude Code plugin marketplace (`orchx-maker-toolkit`) with one plugin, `orchx-maker`, whose source is the repo root. The marketplace entry's `skills` array names each published skill explicitly. That array is what keeps mounted Gemini symlinks and unlisted skills out of the plugin, even when they're present on disk.

Your actual day-to-day Claude Code skill catalog (`bootstrap-worktree`, `summon-profile`, `cast-profile`, etc.) lives globally in `~/.claude/skills/` and is intentionally **not** mirrored into this repo — the two toolkits evolve independently, and several names have already diverged in purpose (e.g. `start-worktree`/`finish-worktree` here vs. `bootstrap-worktree`/`fixup-worktree` globally; `summon-profile` here pulls Claude state *into* Gemini, the global one does the opposite).

## Working in this repo

- Changes to Gemini skill behavior: edit `.gemini/skills/<name>/SKILL.md`, then `mise run build:gemini` and `mise run test` (validates every skill via the `gemini-cli` Homebrew validator).
- Changes to the repo-local Claude skills (`patch-my-hosts`, `llm-wikify`, `browser-test-assist`, `browse`): edit `.claude/skills/<name>/` directly, then `mise run build:claude` (`claude plugin validate --strict`).
- Publishing a new Claude-native skill takes three edits: the skill directory, a `!` allowlist line in `.gitignore`, and an entry in `.claude-plugin/marketplace.json` → `plugins[0].skills`. Miss the last one and the skill validates but never ships.
- The version lives in four places, and `/release` keeps them in step: `GEMINI.md`, `.claude-plugin/plugin.json` (`plugin.json` wins over any `version` on the marketplace entry, so the entry doesn't carry one), the `CHANGELOG.md` heading, and the git tag.
- Do not port or rename `.gemini/skills/*` into `.claude/skills/*` by hand-copying files. A straight file-level mirror would create conflicting/duplicate concepts against the global Claude toolkit. The mount tasks below are the one sanctioned exception: they symlink, never copy, so there's still exactly one source file per skill.

### Creating a skill

This toolkit now targets Claude Code by default. Before writing any files for a new
skill, ask the maintainer the placement questions in `CONTRIBUTING.md` → "Adding a
Skill", in one batch, skipping any the request already answers:

1. **Harness:** Claude (the default), Gemini, or both?
2. **User-level or repo?** User-level goes in `~/.claude/skills/` and never enters
   this repo.
3. **For a repo skill: mountable or repo-specific?** Mountable means globally mounted:
   symlinked into `~/.claude/skills/` (and the Gemini equivalent) so edits go live
   everywhere. Repo-specific means not globally mounted.

"Mountable" here means that global mount. It is not the repo-local test mount that
`mise run mount:claude` does, described below.

### Mounting Gemini skills as Claude Code skills

Because `SKILL.md`'s frontmatter format is Claude-Code-compatible, every skill under
`.gemini/skills/` can also be exercised as a Claude Code skill without duplicating its
source:

- `mise run mount:claude` — symlinks each `.gemini/skills/<name>` into
  `.claude/skills/<name>`. Real, Claude-native skills already in `.claude/skills/`
  (currently `patch-my-hosts`, `llm-wikify`, `browser-test-assist` and `browse`) are left untouched — the task
  skips any target that exists and isn't itself a symlink.
- `mise run unmount:claude` — removes only the symlinks the mount created.
- `mise run test:claude` — first runs `scripts/validate_claude_skills.selftest.cjs`, which
  proves the validator rejects the broken skills in `scripts/fixtures/claude-skills/`,
  and `scripts/claude_global_skill.selftest.cjs` (below, against a throwaway `HOME`),
  then mounts, runs `scripts/validate_claude_skills.test.cjs`
  against everything under `.claude/skills/` (checking `SKILL.md` has the `name` and
  `description` frontmatter Claude Code requires, and that `name` matches the directory),
  then unmounts — a clean, self-contained pass regardless of the outcome.

Mounted symlinks are gitignored (`.gitignore` ignores `.claude/skills/*` except the
explicitly allowlisted real skills), so `mount:claude` never needs to be run before a
commit and never shows up as a diff.

### Installing repo-local Claude skills globally

The real skills in `.claude/skills/` only load in sessions opened in this repo. To use one
from any project, install it into the user-scope catalog as a symlink — the repo stays the
single source file, and an edit here takes effect everywhere:

- `mise run install:claude-global [name...]` — symlinks `.claude/skills/<name>` into
  `~/.claude/skills/<name>`; with no names, every real skill (never `mount:claude`
  mounts). Idempotent. Re-points a symlink that targets somewhere else and prints the old
  target. A real directory with identical content is moved to
  `~/.claude/skill-backups/<name>-<timestamp>` first; one that differs is refused.
- `mise run uninstall:claude-global [name...]` — removes only symlinks that resolve into
  this checkout; anything else is reported and left alone.

Links always target the **main checkout**, resolved via `git rev-parse --git-common-dir`
even when run from a worktree, because a link into a worktree dangles once it's pruned. So
a new skill installs after it merges to `main`. To try one before that, run
`SKILL_SOURCE_ROOT=$PWD mise run install:claude-global <name>` from the worktree, then
re-run it from `main` after the merge so the link stops pointing at the worktree. New Claude Code sessions pick the change up; running ones don't.

Adding a new repo-local skill: create `.claude/skills/<name>/`, add
`!.claude/skills/<name>` to `.gitignore`, name it in this file, then install it.
